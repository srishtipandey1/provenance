# Design Decisions
Every schema, query, and architecture decision in plain language: what, why, and the alternative rejected.

- Docker Compose runs the official `falkordb/falkordb` image, publishes the database and Browser ports (6379 and 3000), and mounts a named volume at `/var/lib/falkordb/data` as documented by FalkorDB. This keeps development data persistent; a host bind mount was not chosen because the project needs portable local persistence.
- Gate 0 reads declared ownership from integration manifests and applies the last matching top-level CODEOWNERS rule to each integration's manifest path; this avoids rescanning every integration subtree and makes the ownership comparison reproducible. ADR metadata is extracted from local text files. GitHub PR sampling uses GraphQL search filtered by merged date and updated-time ordering, requesting files and reviews with 100-item nested limits. GitHub does not expose mergedAt as a pull-request connection sort key, so updatedAt is the ordering proxy; the full-fetch estimate assumes the observed mean cost and latency per page.
- PR ingestion uses the repository pullRequests connection ordered by UPDATED_AT, not the capped Search API. It stops once updatedAt is older than the stored UTC cutoff and independently retains only records whose mergedAt is in-window. Pages are appended as JSONL before atomically advancing the cursor state; cached PR numbers are deduplicated to make replay after interruption safe. The first/retry page size starts at 50 and is halved after timeout or node-limit failures. PR body text is capped at 6,000 characters and redacts email addresses and GitHub token-shaped strings to honor the data-handling rules.
- PR cache records store the GraphQL `body` field rather than `bodyText` so raw Markdown checkbox state is preserved for later surveys. The body remains capped at 6,000 characters and redacted. `__typename` is retained on `mergedBy` and review authors so bot actors can be distinguished without inferring from login names.
- The observed GitHub GraphQL gateway returned non-JSON HTTP 499 during the full fetch. Treat 499 and 504 as transient transport failures alongside 502/503, using the same bounded exponential retry so the durable cursor can resume rather than stopping on a transient gateway response.
- Survey aggregates use unique PR records; reviewer counts exclude bots and the PR author, and reviewer medians/top lists count each reviewer once per PR. The ownership baseline is split over unique PR-integration pairs, with an additional overall unique-PR fraction; only the first 100 fetched reviews/files can contribute, and report metrics flag truncated review/file lists.
- The graph model is documented in `docs/graph_model.md`. Graph loads delete and rebuild only the selected graph, create range indexes on Person.login, Team.handle, Module.key, PR.number, and Decision.id, then use parameterized UNWIND batches of 750 rows. Relationship endpoints are MATCHed separately before MERGE to avoid FalkorDB's documented full-path MERGE duplicate-endpoint behavior. All event timestamps are integer epoch seconds.
- Module mapping is deterministic: integration paths under `homeassistant/components/<name>` and `tests/components/<name>` use `integration:<name>`; other `homeassistant/<second-level>` paths use those two levels as a core key; all remaining files group under `infra:<first-component>` (root files use the filename). Team handles are stored without `@`, while Person logins are case-folded without `@`.
- The zero-owner verification query is limited to integration keys backed by a successfully parsed manifest. Counting every path-inferred integration module also included test-only modules and overstated ownerless integrations.
- Dependency edges retain source kind (`dependency`, `after_dependency`, or `python_import`); imports are parsed once in a single non-test source traversal. Architecture discussion links generate reference-only Decision stubs because discussion contents are not in the local cache; ADR blob links resolve to parsed ADR Decisions. Breaking PR signals create a separate `pr-breaking:<number>` Decision and use DECIDED_AS, keeping the required REFERENCES edge for external architecture references.
- Python import extraction keeps AST as the primary parser and uses an anchored regex only for files that raise SyntaxError, recovering the requested `from` and `import homeassistant.components.<name>` forms. Read failures are counted separately. On this snapshot, 8,794 files parsed by AST, 1,540 were regex-recovered, and 0 were unreadable; this adds 281 unique Python-import edges and raises DEPENDS_ON to 5,152. The leading parse messages include PEP 695/Python 3.12 syntax and invalid multi-exception syntax, so the failures cannot all be attributed to running Python 3.11.
- Reviewer evaluation performs as-of history filtering in parameterized `GRAPH.RO_QUERY` calls with `PR.merged_ts < $as_of` and review/authorship event times before the target. FalkorDB documentation and runtime probes verified the used range predicates, aggregation, `UNION ALL`, list membership, and `exp` decay. G1/G2 expertise aggregates retain person, module, role, and contributing PR numbers.
- Reviewer evaluation uses validation `[t-60d, t-30d)` and test `[t-30d, t)` windows and tunes only on the validation primary slice. `DECLARED_OWNER` and `DEPENDS_ON` have no temporal validity in this graph; the owner baseline and G2 therefore use current snapshots, a limitation disclosed in results.
- Frozen validation settings at `2026-10-15T12:35:27Z`: B3 half-life 14 days; G1 half-life 90 days and author weight 0.5; G2 half-life 90 days, author weight 0, and neighbor factor 0.3. Validation primary size was 1,740. Held-out primary reviewers: n=2,683, oracle ceiling 1.0; hit@3 was B1 0.1439, B2 0.3224, B3 0.4342, G1 0.4532, G2 0.4338. Paired G1-B3 hit@3 difference was 0.0190 (95% CI -0.0045 to 0.0447); G2-B3 was -0.0004 (95% CI -0.0227 to 0.0239). Neither graph method significantly beats recent popularity at hit@3; B3 has higher hit@5 and recall@5, while G1 has higher hit@1 and MRR. Mean query latency was 140.78 ms per scored PR (median 129.15 ms; p95 213.79 ms). Full metrics and slices are in `results/reviewer_eval.json`.
- Round 2 leaves the first artifact and frozen B3/G1/G2 settings unchanged. Each rolling window uses a fixed strict history cutoff at its start; lambda alone is tuned on the immediately preceding 30-day window. A validation interval may be another later-origin fold's test interval, but is strictly pre-test for the origin it tunes; no fold uses its own test labels. Fold A (Sep 15-Oct 15) is labeled POST-HOC; B and C are the confirmatory earlier windows. Fold history availability is 150/120/90 days, and the selected lambdas are 1/1/2 on validation n=1,740/1,072/1,324.
- G3 normalizes frozen G1 and B3 scores over the union of all G1 candidates and B3's top 20; G3b retains G1 order and backfills to 10 from B3. Both use as-of graph aggregates retaining global REVIEWED PR IDs and per-person/module/role support PR IDs. The indexed coldness query collects prior PR IDs per integration once, then computes unique integration unions per target in Python.
- Fold A diagnostics: G1 had fewer than five candidates on 421/2,683 PRs (15.69%); among the remaining 2,262 PRs, G1 hit@5=0.5097. The global oracle is 1.0, while the module-local oracle is 1,894/2,683=0.7059.
- Pooled unseen B/C (n=2,812): B3 hit@3=0.4257; G1=0.4772; G3=0.5441. G3-B3 hit@3 difference=0.1184 (95% CI 0.1035 to 0.1337); G3-G1=0.0669 (95% CI 0.0530 to 0.0811). G3 also improves hit@5, recall@5, and MRR over both parents, but B3 has higher hit@1 (0.3137 vs G3 0.3076); G3b has the highest hit@1 (0.3243). Claim a top-K gain, not universal superiority. All requested fold, slice, and CI metrics are in `results/reviewer_eval_round2.json`.
