# Design Decisions
Every schema, query, and architecture decision in plain language: what, why, and the alternative rejected.

- Docker Compose runs the official `falkordb/falkordb` image, publishes the database and Browser ports (6379 and 3000), and mounts a named volume at `/var/lib/falkordb/data` as documented by FalkorDB. This keeps development data persistent; a host bind mount was not chosen because the project needs portable local persistence.
- Gate 0 reads declared ownership from integration manifests and applies the last matching top-level CODEOWNERS rule to each integration's manifest path; this avoids rescanning every integration subtree and makes the ownership comparison reproducible. ADR metadata is extracted from local text files. GitHub PR sampling uses GraphQL search filtered by merged date and updated-time ordering, requesting files and reviews with 100-item nested limits. GitHub does not expose mergedAt as a pull-request connection sort key, so updatedAt is the ordering proxy; the full-fetch estimate assumes the observed mean cost and latency per page.
- PR ingestion uses the repository pullRequests connection ordered by UPDATED_AT, not the capped Search API. It stops once updatedAt is older than the stored UTC cutoff and independently retains only records whose mergedAt is in-window. Pages are appended as JSONL before atomically advancing the cursor state; cached PR numbers are deduplicated to make replay after interruption safe. The first/retry page size starts at 50 and is halved after timeout or node-limit failures. PR body text is capped at 6,000 characters and redacts email addresses and GitHub token-shaped strings to honor the data-handling rules.
- PR cache records store the GraphQL `body` field rather than `bodyText` so raw Markdown checkbox state is preserved for later surveys. The body remains capped at 6,000 characters and redacted. `__typename` is retained on `mergedBy` and review authors so bot actors can be distinguished without inferring from login names.
- The observed GitHub GraphQL gateway returned non-JSON HTTP 499 during the full fetch. Treat 499 and 504 as transient transport failures alongside 502/503, using the same bounded exponential retry so the durable cursor can resume rather than stopping on a transient gateway response.
- Survey aggregates use unique PR records; reviewer counts exclude bots and the PR author, and reviewer medians/top lists count each reviewer once per PR. The ownership baseline is split over unique PR-integration pairs, with an additional overall unique-PR fraction; only the first 100 fetched reviews/files can contribute, and report metrics flag truncated review/file lists.
- The graph model is documented in `docs/graph_model.md`. Graph loads delete and rebuild only the selected graph, create range indexes on Person.login, Team.handle, Module.key, PR.number, and Decision.id, then use parameterized UNWIND batches of 750 rows. Relationship endpoints are MATCHed separately before MERGE to avoid FalkorDB's documented full-path MERGE duplicate-endpoint behavior. All event timestamps are integer epoch seconds.
- Module mapping is deterministic: integration paths under `homeassistant/components/<name>` and `tests/components/<name>` use `integration:<name>`; other `homeassistant/<second-level>` paths use those two levels as a core key; all remaining files group under `infra:<first-component>` (root files use the filename). Team handles are stored without `@`, while Person logins are case-folded without `@`.
- The zero-owner verification query is limited to integration keys backed by a successfully parsed manifest. Counting every path-inferred integration module also included test-only modules and overstated ownerless integrations.
- Dependency edges retain source kind (`dependency`, `after_dependency`, or `python_import`); imports are parsed once in a single non-test source traversal. Architecture discussion links generate reference-only Decision stubs because discussion contents are not in the local cache; ADR blob links resolve to parsed ADR Decisions. Breaking PR signals create a separate `pr-breaking:<number>` Decision and use DECIDED_AS, keeping the required REFERENCES edge for external architecture references.
- Python import extraction keeps AST as the primary parser and uses an anchored regex only for files that raise SyntaxError, recovering the requested `from` and `import homeassistant.components.<name>` forms. Read failures are counted separately. On this snapshot, 8,794 files parsed by AST, 1,540 were regex-recovered, and 0 were unreadable; this adds 281 unique Python-import edges and raises DEPENDS_ON to 5,152. The leading parse messages include PEP 695/Python 3.12 syntax and invalid multi-exception syntax, so the failures cannot all be attributed to running Python 3.11.
- Reviewer evaluation performs as-of history filtering in parameterized `GRAPH.RO_QUERY` calls with `PR.merged_ts < $as_of` and review/authorship event times before the target. FalkorDB documentation and runtime probes verified the used range predicates, aggregation, `UNION ALL`, list membership, and `exp` decay. G1/G2 expertise aggregates retain person, module, role, and contributing PR numbers.
- Reviewer evaluation uses validation `[t-60d, t-30d)` and test `[t-30d, t)` windows and tunes only on the validation primary slice. `DECLARED_OWNER` and `DEPENDS_ON` have no temporal validity in this graph; the owner baseline and G2 therefore use current snapshots, a limitation disclosed in results.
- Frozen validation settings at `2026-10-15T12:35:27Z`: B3 half-life 14 days; G1 half-life 90 days and author weight 0.5; G2 half-life 90 days, author weight 0, and neighbor factor 0.3. Validation primary size was 1,740. Held-out primary reviewers: n=2,683, oracle ceiling 1.0; hit@3 was B1 0.1439, B2 0.3224, B3 0.4342, G1 0.4532, G2 0.4338. Paired G1-B3 hit@3 difference was 0.0190 (95% CI -0.0045 to 0.0447); G2-B3 was -0.0004 (95% CI -0.0227 to 0.0239). Neither graph method significantly beats recent popularity at hit@3; B3 has higher hit@5 and recall@5, while G1 has higher hit@1 and MRR. Mean query latency was 140.78 ms per scored PR (median 129.15 ms; p95 213.79 ms). Full metrics and slices are in `results/reviewer_eval.json`.
- Round 2 leaves the first artifact and frozen B3/G1/G2 settings unchanged. Each rolling window uses a fixed strict history cutoff at its start; lambda alone is tuned on the immediately preceding 30-day window. A validation interval may be another later-origin fold's test interval, but is strictly pre-test for the origin it tunes; no fold uses its own test labels. Fold A (Sep 15-Oct 15) is labeled POST-HOC; B and C are the confirmatory earlier windows. Fold history availability is 150/120/90 days, and the selected lambdas are 1/1/2 on validation n=1,740/1,072/1,324.
- G3 normalizes frozen G1 and B3 scores over the union of all G1 candidates and B3's top 20; G3b retains G1 order and backfills to 10 from B3. Both use as-of graph aggregates retaining global REVIEWED PR IDs and per-person/module/role support PR IDs. The indexed coldness query collects prior PR IDs per integration once, then computes unique integration unions per target in Python.
- Fold A diagnostics: G1 had fewer than five candidates on 421/2,683 PRs (15.69%); among the remaining 2,262 PRs, G1 hit@5=0.5097. The global oracle is 1.0, while the module-local oracle is 1,894/2,683=0.7059.
- Pooled unseen B/C (n=2,812): B3 hit@3=0.4257; G1=0.4772; G3=0.5441. G3-B3 hit@3 difference=0.1184 (95% CI 0.1035 to 0.1337); G3-G1=0.0669 (95% CI 0.0530 to 0.0811). G3 also improves hit@5, recall@5, and MRR over both parents, but B3 has higher hit@1 (0.3137 vs G3 0.3076); G3b has the highest hit@1 (0.3243). Claim a top-K gain, not universal superiority. All requested fold, slice, and CI metrics are in `results/reviewer_eval_round2.json`.
- Per-PR as-of scoring with the same frozen parameters and Fold A lambda exactly reproduces round-1 B3 hit@3: 0.4342154305 on n=2,683. The fixed-window B3 result is 0.2974282520, a +0.1367871785 difference. Therefore the within-window history regime fully explains the B3 score gap; this per-PR comparison is saved separately in `results/reviewer_eval_round2_per_pr.json` and does not alter existing artifacts.
- FalkorDB's variable-length dependency path query returned no rows when an `UNWIND` alias was used inside the terminal node's property map (`{key: root_key}`), despite matching nodes and edges. Match the path without a map constraint and filter with `target.key IN $module_keys` in `WHERE`; a tiny graph test proves the corrected query returns the dependent. The single-edge depth-1 query, zero-owner verification query, all nine ingestion relationship loaders, and evaluator query set were checked on tiny fixtures and do not exhibit this failure.
- The risk report scores the union of the top 15 modules by human-review concentration and top 15 by PageRank. Its score is a weighted average of top-person review share (0.35), ownership drift (0.30), candidate-normalized PageRank (0.20), and candidate-normalized distinct reverse-dependent count (0.15); these weights live in `ToolConfig`. The report stores the per-call timings and exact component facts for its top five rows. No new dependency was added.
- The G3 tool bundle groups module expertise once per person/module/PR even when multiple review-state edges exist, while retaining all supporting edge IDs. Global review-event counts remain the evaluator's popularity tie-break. This fixes tool-only double counting; evaluator code and published metric artifacts are unchanged.
- Maintainer loss reports `distinct_dependents_affected` as the union of dependent Module keys across newly uncovered modules; `summed_dependent_edges` is the sum of those per-module distinct counts, so overlaps are visible rather than double-counted as distinct impact. Both values are included in the replayed dependency-impact Fact.
- The verifier has no LLM or network path. It resolves facts only from draft ToolResults, replays through the registered query and extractor, uses exact integer/string comparison and relative float tolerance `1e-9`, grounds displayed numeric tokens, checks per-claim as-of agreement, and adds a static-snapshot caveat for `DECLARED_OWNER`/`DEPENDS_ON` facts. Proof Cypher substitutes registry parameters for display only and is never executed.
- The deterministic router resolves module aliases from `modules.list@1`, resolves GitHub logins case-insensitively through `person.by_login@1`, and recognizes PR numbers in `PR N` and `#N` forms. Unsupported question forms abstain with the supported-query list; all answer claims cite qualified ToolResult fact IDs to avoid local `F1` collisions.
- Live ownership-drift ranking for the report uses one parameterized `ownership.drift.inputs.all@1` query for modules with at least ten recent PRs. It groups owner and human activity rows in the registered extractor and ranks by the existing configured drift score; a temporary-graph regression test covers the query and replay.
- Graph-dependent pytest items are preflighted once using the official client's connection ping. If unavailable, only graph-dependent tests skip with the host/port and `docker compose up -d` instruction; no container is started by tests.
- Maintainer-loss impact facts retain the dependent-module set per uncovered root, the distinct union size, and the sum of per-root distinct counts. The first is used for each module's impact; the union prevents shared dependents from being reported twice as distinct impact.
- The no-LLM answer verifier assigns `VERIFIED`, `UNSUPPORTED`, or `CONTRADICTED`; qualified fact references use `result_index:tool_name:fact_id` because local fact counters restart in each ToolResult. Numeric tokens are checked against numeric leaves, floats use relative tolerance 1e-9, and only the decision-list extractor is treated as unordered. Rendered Cypher is display-only.
- Deterministic routing recognizes seven supported question classes, resolves module aliases from the registered module catalog, case-folds known logins, and extracts PR numbers in either `PR N` or `#N` form. Each answer claim is assembled from cited tool facts and verified before display; unknown question forms abstain.
- The live ownership-drift report considers every module with at least ten PRs in the configured activity window. It batches owner and human-activity rows through the registered query and sorts them with the configured drift score; the top five are written alongside declared owners and behavioral top five.
- The vector baseline uses one local embedding per cached merged PR from title, labels, the first 800 body characters, and up to eight changed top-level paths. It uses Apache-2.0 `sentence-transformers/all-MiniLM-L6-v2` (22.7M parameters, 384 dimensions, default 256 word-piece truncation) and caches normalized embeddings under `data/cache/rag`; this keeps retrieval graph-free and repeatable. `sentence-transformers>=5,<6` is added because no embedding stack was installed. CPU PyTorch is installed from its CPU wheel index to avoid unnecessary CUDA packages; expected model weights are about 91 MB and the full CPU stack about 0.5–1.5 GB.
- RAG tuning searches k in {5, 10, 20, 40} and similarity exponents in {1, 2} using only the validation window immediately preceding each fold. Test retrieval uses strict `merged_ts < target merged_ts`, excludes bots and the target author, and gives each reviewer at most one vote per retrieved PR. Existing B3/G1/G3 aggregate metrics are loaded from the frozen per-PR artifact; only per-target G3 scores needed for paired confidence intervals are regenerated with the evaluator's frozen helper. Existing result artifacts are not modified.
- The LLM provider client uses the existing `httpx` dependency, keeps provider configuration and env overrides in one `LLMConfig`, counts retries against the four-call budget, and caches responses by provider/model/messages/tools/response format. Availability probes use model-list GETs only; they do not send chat-completion requests. Error strings are scrubbed of configured and key-shaped secrets.
- The LLM agent passes graph facts in escaped JSON data blocks, calls only registry tool functions after JSON Schema validation and resolver normalization, and runs the same verifier before exposing claims. The user question and graph strings are not interpolated into Cypher; prompt-injection content remains quoted data. Deterministic fallback is used when no provider responds or strict claims JSON cannot be parsed twice.
- Provider verification (2026-10-16): Groq's OpenAI-compatible base is `https://api.groq.com/openai/v1` ([OpenAI compatibility](https://console.groq.com/docs/openai)); `openai/gpt-oss-120b` advertises Tool Use, JSON Object Mode, and JSON Schema Mode ([model page](https://console.groq.com/docs/model/openai/gpt-oss-120b)). Groq's Free Plan table lists 30 RPM, 1,000 RPD, 8K TPM, and 200K TPD for this model ([rate limits](https://console.groq.com/docs/rate-limits)); the page notes exact limits can vary by organization.
- Provider verification (2026-10-16): Gemini OpenAI compatibility uses `https://generativelanguage.googleapis.com/v1beta/openai/`, and documents function calling and structured JSON for `gemini-3.8-flash` ([compatibility](https://ai.google.dev/gemini-api/docs/openai), [models](https://ai.google.dev/gemini-api/docs/models)). The published rate-limit docs say quotas vary by project, model, and usage tier and direct users to AI Studio for exact live limits; no universal free-tier RPM/TPM is claimed ([rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)).
- Provider verification (2026-10-16): local Ollama's OpenAI-compatible chat endpoint is `http://localhost:11434/v1/`; its docs list tool and `response_format` support, and tool-calling examples use Qwen 3 ([OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility), [tool calling](https://docs.ollama.com/capabilities/tool-calling), [structured outputs](https://docs.ollama.com/capabilities/structured-outputs)). The local server was not reachable during this check, so it remains optional.
- `httpx` is already a direct project dependency and is used for the provider-agnostic OpenAI-compatible transport; no SDK dependency is added. The planned RAG encoder is `sentence-transformers/all-MiniLM-L6-v2` (22.7M parameters, 384-dimensional vectors, Apache-2.0); approximate FP32 weights are 91 MB. The CPU PyTorch installation is estimated at 0.5–1.5 GB total downloads; report this before installation. On this 14-core CPU, estimate 5–15 minutes for 10,285 short documents, then measure actual runtime.
- The text-only reviewer baseline uses one cached normalized all-MiniLM-L6-v2 CPU embedding per merged PR, built from title, labels, the first 800 body characters, and unique changed top-level paths. Retrieval is strictly as-of (`merged_ts < target merged_ts`), excludes the target, target author, and bot reviewers, and gives each human reviewer at most one similarity-weighted vote per retrieved PR. Cache keys cover model name, PR numbers, and document text; artifacts remain under gitignored `data/cache/`.
- RAG searches k in {5, 10, 20, 40} and cosine-similarity exponents in {1, 2}; each Fold A/B/C configuration is selected only on its immediately preceding 30-day validation interval by hit@3, then MRR, then recall@5. The primary target/ground-truth population reuses reviewer-evaluator helpers and is checked against saved per-PR fold counts. Published B3/G1/G3 aggregates are read from `results/reviewer_eval_round2_per_pr.json`; per-target graph rankings are regenerated with frozen evaluator helpers only where paired intervals and per-PR slices require them.
- The RAG failure audit reuses parameterized read-only evaluator history queries at each target's merge timestamp, including reviewer and author events strictly before the target, to check whether a RAG top-three candidate had any prior activity in any touched module. The scoreboard reads B3/G1/G3 pooled aggregates from the frozen per-PR artifact and uses RAG-run same-regime calculations for B1/B2 and slices. NumPy is declared directly because the baseline uses it for embedding normalization, similarity ranking, and cached dense arrays; its existing installed version was used without installation.
- Live LLM verification (2026-10-16): two real graph questions used 7 Groq chat requests total. The sensor-risk answer had no verified claims and one unsupported claim was removed; the epenet answer exhausted its four-call question budget and returned a verified deterministic fallback. One additional Gemini request returned `OK` from `gemini-3.8-flash`, confirmed in Google's [OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai) and [current model list](https://ai.google.dev/gemini-api/docs/models). Total live chat requests: 8; no standalone Groq smoke request was made.
- Free-form LLM claim prose was replaced after a real sensor answer cited nonexistent qualified fact IDs and included numbers absent from the cited fact values. The model now returns only ordered selected fact IDs plus an optional summary of at most two sentences; code constructs one claim from each selected Fact's stored text with exactly that fact's qualified ID, then the existing verifier replays every claim. Unknown IDs are ignored/countable. A summary with ungrounded numbers remains visible only as a verifier-removed claim; fact claims remain independently verified. Tool selection is capped at two rounds and the total question budget at three calls, including one parse retry only when budget remains. On failure, the router reuses matching computed ToolResults; it does not rerun those tools.
- Subgraph export uses two registered parameterized read queries, `api.subgraph.nodes_by_id@1` and `api.subgraph.edges_by_id@1`, matching internal IDs with `WHERE id(entity) IN $ids`. FalkorDB documents `id()`, `labels()`, and `type()`; IDs are ephemeral and may change on graph rebuild. Output prioritizes edge endpoints, caps at 150 nodes/300 edges, sets `truncated`, limits properties to login/key/name/number/title/status/kind/ts, and redacts email/token-shaped strings. Tiny-graph tests verified ID matching and endpoint inclusion.
- The FastAPI service only uses registered parameterized `GRAPH.RO_QUERY` reads. Health uses grouped label/type counts and model-list provider probes. Neighborhood uses registered module, owner/activity, and direct-dependency queries; direct dependents are aggregated and capped at 30, behavioral people are ranked by distinct activity PRs then review PRs. API LLM/auto requests are limited to six per client per minute and reserve at most three calls from a persisted daily counter (default 100, configurable); deterministic questions have a 30-second in-memory TTL cache. Errors are sanitized, logs carry request IDs without bodies, and CORS defaults to localhost:5173. No new dependency was added.
- Live fact-selection verification (2026-10-16): sensor risk used 3 Groq calls and all four claims verified. The epenet run used 3 calls, then its pre-router-fix fallback verified 21/22 fact claims; the verifier removed C22 because its stored sentence contained an ungrounded `2`. A later tiny-graph regression verifies that the router now reuses a matching maintainer result and returns its single verified claim without rerunning the tool. No additional live calls were made after the six-request cap was reached.
- Proof Cypher is display-only: facts sharing a query ID render once, long list parameters remain named placeholders with one abbreviated parameter-header binding, and repeated UNION references reuse the placeholder. Reviewer-bundle output removes optional aliases and shortens local variable names for readability. The full values remain in `proof.params`; verification still calls `recompute_fact` with each exact `Fact.params`, never the rendered text.
- Subgraph totals are the unique nonnegative node/edge IDs in the verifier evidence bundle before capping. The exporter fetches only the top 150 priority nodes and 300 priority edges, avoiding full-graph scans with thousands of internal IDs; required direct path edges are selected from existing registered as-of depth queries for the highest-impact roots. Priority order is subject, cited/derived direct entities, declared owners, then fact-weighted evidence. Negative `-1` query sentinels are not graph IDs. `truncated` compares returned matched rows to full evidence totals and the note describes the omitted remainder.
- The reviewer bundle's aggregate `id(review)` projection returned PR-number-shaped values on the real graph, so it is no longer trusted as edge evidence. `reviewer.support_edges@1` returns scalar as-of review/touch edge IDs and person/PR/module node IDs for the top three candidates, is cited by the deterministic reviewer claim, and is capped at 120 rows. The reviewer bundle still provides ranking values but no longer contributes its invalid aggregate edge column to evidence.
- Final deterministic real-graph proof measurements (2026-10-16, no LLM): canonical totals live in PROJECT_STATE.md (epenet 258 of 17,402 edges; sensor 236 of 14,690 edges; PR 179264 reviewer 150 of 2,781 nodes and 224 of 3,810 edges).
- Proof display rule: rendered Cypher abbreviates lists over 8 items, exact values stay in proof.params and replay always uses exact params; subgraphs are priority-ranked subject first, then directly cited entities, then weighted evidence, with exact before-cap totals and a relevance note; reviewer evidence uses reviewer.support_edges@1 because the UNION aggregate ID projection returned PR numbers in an ID column, so that aggregate column was removed from evidence.
- Coordination state is persisted in the tenant's FalkorDB graph, not agent memory: UUID-keyed Task/Episode nodes, separate synthetic Agent claimants (so workflow names never pollute public GitHub Person logins), and explicit CLAIMED_BY/PRODUCED/USED_FACT/DEPENDS_ON edges. Episodes store registered query IDs, exact params, extractor names, and original evidence node/edge IDs; USED_FACT points to the existing evidence nodes because graph edges cannot themselves be relationship endpoints. MERGE makes retries idempotent for the same task/episode IDs. Task/Episode lookup indexes are part of graph-loader index creation.
- Workflow agents wrap only the existing deterministic tools. RiskAgent depends on the ReviewerAgent task in the orchestration; HistorianAgent queries its latest Episode from the graph before writing each run. Tenant demonstrations copy only selected modules and their mutual dependency links, associated PR/person activity, and declared owners into two distinct graphs, run the same deterministic router question, check one task per tenant, and delete the temporary tenant graphs. The concurrency demo writes independent task/episode pairs to an explicitly selected existing graph; those probe records are intentionally retained.
- FalkorDB coordination queries use the registered parameterized query registry. The tenant demo uses a small set of registered typed copy queries rather than interpolating labels or Cypher fragments. No new dependency was added.
- Coordination agents check `CALL db.indexes()` through a registered read query and create only missing Task/Episode range indexes through registered DDL queries. This supports an already-loaded `provenance_ha` without forcing a destructive data rebuild; fresh graph loads also create the indexes. Tenant copies index every label they look up.
- The frontend dashboard reuses the existing FastAPI endpoints without backend changes. It uses Vite + React + TypeScript, a small typed same-origin /api client with a dev proxy to 127.0.0.1:8000, and a dependency-free SVG neighborhood graph. Only VERIFIED claims are presented as verified; truncated subgraphs are labeled partial rather than complete. No secrets are stored in frontend code.
- The dashboard redesign keeps the same API contracts and uses an evidence-ledger visual language (paper background, ink hairlines, serif headlines, mono evidence, VERIFIED stamps) instead of generic dark cards, so judges can distinguish declared structure from machine-checked behavior at a glance. The neighborhood graph uses two deterministic rings by node id with shape-per-type encoding (square subject module, circles for people, diamonds for teams), hover isolation and click-to-pin, and never invents nodes outside returned subgraph rows. Risk rows dispatch a window event that the impact panel listens to, so no backend change was needed for cross-panel tracing.
